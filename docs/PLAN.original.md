# PhotoTrace 首版实施计划（修订版）

更新日期：2026-10-09  
文档状态：当前计划，尚未开始实现。

## 一、目标与范围

首版交付可直接打开的单文件 `phototrace.html`，主目录为 `D:\codex\phototrace`。使用内联 HTML、CSS 和 JavaScript，浏览器自动保存，支持 JSON 备份与恢复。

系统继续采用：

- **统一数据、两个视图：** 项目视图和人物视图共用人物任务记录。
- **三级组织：** 项目 → 可选团体 → 人物任务；人物身份跨项目复用。
- **四阶段进度：** 导入 30%、初筛 30%、修图 30%、发布 10%。
- **自动状态：** 由真实业务属性推导；挂起、资源占用、存储位置分别维护。

先完成真实业务闭环和数据可靠性，不增加 EXIF 读取、文件夹扫描、外部软件联动、微博同步、耗时统计或跨设备自动同步。

**UI 动画明确参考 Trello Pro，并纳入首版交付与验收。** 保持界面轻量，同时借鉴原看板的卡片展开／收回和布局过渡体验。

### 现有 Trello Pro 的定位与复用边界

参考软件为 **Trello Pro**，位于 `D:\codex\benchmark\gemini`，说明文档为 [README.md](D:/codex/benchmark/gemini/README.md)。依用户要求，该 README 已由 GPT-6.1-sol 子智能体阅读，主智能体未直接读取。当前掌握的是 README 描述，尚未检查源码、运行效果或代码复用质量。

Trello Pro 是本地离线的通用任务看板，README 描述了单文件 HTML、原生 JavaScript、多项目 Tab、卡片详情、颜色标签、拖拽、浏览器自动保存及 JSON 导出恢复。PhotoTrace 将它作为明确的交互参考和代码复用候选。

实现路线是：**在 PhotoTrace 目录交付独立应用，摄影业务模型重新设计；开发前检查 Trello Pro 源码，优先迁移能独立使用、符合本计划约束的界面与通用逻辑。** 原 Trello Pro 文件和已有浏览器数据保持独立。

| 原有能力 | PhotoTrace 中的处理 |
|---|---|
| 单文件 HTML、原生 CSS／JavaScript、离线打开 | 沿用技术路线，保持不需要后端或构建服务 |
| 看板卡片、详情弹窗、颜色标识、快捷编辑 | 借鉴交互；源码检查后优先复用与通用任务模型解耦的部分 |
| 卡片展开／收回、FLIP 让位等 UI 动画 | 作为明确的动效参考，检查源码并观察实际效果后复用适配；将布局过渡用于业务状态更新引起的自动换列、排序和筛选 |
| 浏览器自动保存 | 参考通用实现，使用独立存储键，补齐原子提交与保存失败处理 |
| JSON 导出与导入入口 | 可复用文件选择、下载等通用逻辑；摄影存档结构、关联校验、预览及恢复保护独立实现 |
| 多项目 Tab 和“全部看板” | 可参考导航形式，不把其 Dashboard、通用项目或列表直接等同于摄影项目、团体及人物视图 |
| 卡片跨列、跨项目拖拽 | 不移植到摄影流程，防止绕过状态推导和任务归属约束 |
| 清单、截止日期、主题等通用功能 | 不因参考软件已有就加入首版，按本计划的摄影需求控制范围 |

源码检查重点是数据结构、状态变更入口、DOM 与业务逻辑的耦合、保存恢复路径、动画实现，以及拟复制代码的许可证。能在不依赖旧任务模型的情况下独立迁移且通过对应测试的代码予以复用；耦合过深或无法满足一致性要求的部分按本计划重写，不为复用保留无关功能。

区别的核心在于：Trello Pro 的“项目 → 列表 → 卡片”服务于自由任务管理；PhotoTrace 需要稳定人物身份、项目公共初筛、跨项目人物任务、自动状态和固定权重进度。因此业务数据结构不能直接照搬，但这不妨碍复用经过检查的界面和基础工具代码。

## 二、修订后的业务规则

### 1. 相关数量统一编辑、统一校验、一次提交

原片总数、待筛选数、初筛入选数、精修导出数放在同一个“编辑数量”区域。

操作流程为：

**进入编辑 → 修改多个字段 → 检查最终结果 → 确认必要的状态回退 → 一次保存。**

- 编辑期间允许字段之间暂时不一致，不因中间值矛盾而阻止继续输入。
- 保存时针对完整候选数据统一校验。
- 全部通过后一次更新数据、进度和两个视图；失败时不写入任何一部分，保留输入供修正。
- 取消编辑则放弃整个草稿。
- 如果修改会触发重新初筛，数量修改与状态回退属于同一次提交；取消确认不会只保存其中一半。

例如原片 100 张、待筛选 0 张、入选 20 张，可以同时改为待筛选 90 张、入选 5 张，然后提交，不会被中途出现的“入选超过已浏览”卡住。

数量校验区分两类：

| 类型 | 处理方式 |
|---|---|
| 非整数、负数、待筛选超过原片、入选超过已浏览 | 阻止提交，并指出矛盾字段 |
| 精修导出超过当前入选数 | 显示需确认的提示；允许保留真实成果，不自动扣减 |

第二类采用提示，是因为重新初筛或调整候选范围后，已有导出成果仍可能真实存在。未知数量保持空值，不用 0 冒充。

### 2. 重新初筛保留已有成果与进度贡献

首次初筛完成时，仍通过“完成初筛并确认人物”建立人物任务，名单允许为空。

已经确认过人物名单的项目重新初筛时：

- 保留人物任务、修图和发布标记、发布链接及实际导出数量。
- 宏观状态回到“待筛选”；若项目挂起，仍显示在挂起列。
- 人物任务暂不出现在人物视图中，在项目详情的“已有成果”区域保留可查。
- 重新初筛期间暂停人物状态编辑，待再次确认名单后恢复。
- **已有有效人物任务的修图、发布贡献继续计算，不因重新初筛而清零。**
- 再次确认名单时复用原任务；不再处理的人物通过排除标记保留，不直接删除成果。

首次建立项目、从未确认人物名单时，后两阶段仍不贡献进度。这样可以区分“尚不知道要处理谁”与“已完成工作后补筛”。

### 3. 实际成果与有效任务分开统计

“不再处理”表示退出剩余工作量，不代表此前没有修过或发布过。

| 统计口径 | 内容 | “不再处理”的影响 |
|---|---|---|
| 实际成果 | 人工记录的精修导出张数、当前仍标为修图／发布完成的人物数及链接 | 保留 |
| 有效任务 | 未被排除的人物任务及其完成情况 | 从分子、分母同时排除 |
| 综合进度 | 公共阶段进度，加上有效任务完成率 | 重新计算 |

卡片优先显示有效任务完成情况，如“修图 2/4、发布 1/4”；项目详情同时展示实际成果。

实际成果依据当前记录计算，不新增历史事件日志，也不声称能够统计每次导出或发布的历史累计次数。

### 4. 零分母按 100%，完成原因明确区分

采用已确定的规则：

- 人物名单已经确认后，有效人数为 0，修图与发布阶段均按 100% 计算。
- 从未确认人物名单时，不因为人数为 0 自动完成。
- 原片数量未知不等于 0；明确为 0 的项目仍需完成初筛确认。

为避免把“无需发布”误写成“实际发布”，最后一列改为 **“已完成”**。五列为：

**挂起 → 待筛选 → 已筛选 → 已修图 → 已完成**

完成卡片显示原因标签：

- **已发布：** 所有有效人物均完成发布。
- **无需后续处理：** 已确认没有有效人物任务。

两种情况都可以达到 100%，但实际发布人数和发布链接按真实记录统计。人物视图仍使用“待修图／待发布／已发布”。

### 5. 资源开关只控制进度条显示

是否进行中，仍由 iPad 筛图资源或像素蛋糕修图资源的占用决定。

- 无论是否进行中，内部始终计算完整进度。
- 持久保存数量、完成标记等源数据；百分比随时重新推导，不另存一份可能过期的权威进度。
- 释放资源只隐藏进度条，不改变数字、完成状态或计算结果。
- 挂起与资源占用独立；挂起但仍占用资源时显示提示，不自动释放。

## 三、页面与操作

### 项目总览与详情

总览每张卡片代表一次拍摄，展示日期、评级、关键数量、有效人物完成情况和资源标记。仅进行中项目显示进度条。

支持名称、人物、团体搜索，以及评级、日期、资源筛选。项目评级决定总览排序，团体评级用于项目内部排序，不反向改变项目评级。

详情集中提供：

- 数量编辑与阶段摘要。
- 按团体分组的人物任务。
- 资源占用、存储位置、云备份与长期留档。
- 场地、设备和备注等可选信息。

不通过跨列拖拽改变业务状态。

### UI 动画

以 Trello Pro 的实际交互效果为参考，开发前检查其动画源码并观察效果；README 中提及的动画能力尚未通过运行验证，不预先承诺原代码可以直接搬用。

- **卡片与详情的连续过渡：** 参考原看板的展开／收回效果，让用户能追踪当前详情对应哪张卡片；关闭后回到该卡片的最新位置，若卡片已被筛选隐藏，则平顺关闭详情。
- **布局变化：** 参考 FLIP 让位动画。业务状态更新后卡片自动换列，或因评级、筛选发生重排时，用位移与让位呈现变化；不因此启用跨列拖拽修改状态。
- **操作反馈：** 按钮、勾选、分组展开和进度条变化采用与参考看板协调的短过渡；批量更新集中呈现，不逐张排队播放长动画。
- **实现约束：** 动画时长、缓动和位移风格从源码与实际效果中提取并统一管理；数据保存与状态推导不依赖动画完成。连续点击、切换和更新应能中断或接续动画，不留下遮罩、错位或失去响应的控件。
- **兼容性：** 保持单文件、无外部运行依赖；浏览器不支持所用过渡能力时使用简单淡入淡出，系统开启减少动态效果时取消大幅位移。

### 人物身份与交叉视图

人物使用稳定 ID，同名人员允许存在；同一项目与同一人物只建立一个任务。同一天的不同活动保持独立。

人物视图按“待修图／待发布／已发布”组织任务，显示拍摄日期和活动名。任何视图中的有效修改都更新同一份数据，再同步刷新相关页面。

“不再处理”默认折叠保留；重新初筛中的任务暂时隐藏。

### 人物批量操作

在项目详情和人物视图中，支持勾选多条明确的人物任务，批量：

- 标记或撤销修图完成。
- 标记或撤销发布完成。
- 标记不再处理或恢复处理。

批量操作统一预校验、一次提交：

- 批量发布要求所选任务全部完成修图；不满足时列出问题任务，不静默跳过。
- 撤销修图若会影响已发布状态，先列出影响范围，确认后同步撤销相应发布标记，保留链接。
- 不再处理保留成果；恢复处理重新加入有效任务统计。
- 任一任务校验失败，整批不提交。

## 四、实现与数据保护

### 单文件内部结构

代码按职责划分为业务计算、统一数据操作、持久化和界面四部分。

所有编辑采用一致流程：

**生成候选数据 → 校验 → 确认影响 → 尝试保存 → 刷新视图。**

数量编辑和批量人物操作使用同一套提交机制，避免出现部分保存、部分刷新。

自动保存使用独立的 `localStorage` 命名空间。失败时保留输入和最后成功存档，明确显示未保存，并提供导出当前工作数据的入口。启动发现损坏数据时，禁止用空数据覆盖。

### JSON 备份与恢复

存档保留格式标识、版本、导出时间，以及项目、团体、人物、人物任务、存储信息和设置。状态与百分比在恢复后重新推导。

恢复流程保持：

1. 读取并校验文件格式、版本、字段、数量关系、ID 与关联完整性。
2. 预览项目、人物和任务数量，说明完整替换的影响。
3. 提供当前数据导出，并保存恢复前快照；快照保存失败则不继续替换。
4. 确认后整体恢复，保存失败则保留原存档。

首版只做完整恢复，不做存档合并，不直接导入通用看板格式。未知版本拒绝恢复，不猜测字段含义。

恢复快照服务于数据保护，不扩展为进度修改历史。

## 五、实施顺序与验收

实施顺序为：

1. 检查 Trello Pro 源码及拟复用代码的许可证，观察其卡片展开／收回和布局动画，按上述边界确定并记录可移植的界面、动画与通用逻辑。
2. 数据结构、纯业务计算、状态推导与校验。
3. 数量草稿和原子提交机制。
4. 项目管理、初筛确认、人物任务及双视图，并整合符合约束的参考软件组件与 UI 动画。
5. 批量人物操作、重新初筛和成果统计。
6. 自动保存、JSON 备份恢复与真实文件测试。
7. 使用日常拍摄记录走查，再做必要的界面调整。

重点验收：

| 场景 | 预期结果 |
|---|---|
| 已导入，2300 张原片，待筛选 1380 张 | 总进度 42%，处于待筛选 |
| 公共流程完成，4 人中修完 2 人、发布 1 人 | 总进度 77.5%，处于已筛选 |
| 上述项目没有占用资源 | 内部结果不变，总览不显示进度条 |
| 同时修改原片、待筛选和入选数字 | 只校验最终组合，通过后一次保存 |
| 数量草稿最终无效或取消回退确认 | 原数据全部保持不变，输入可继续修正 |
| 已完成项目重新初筛 | 成果及后期进度贡献保留，宏观状态回退，人物视图暂时隐藏 |
| 将已修完或已发布人物标为不再处理 | 实际成果保留，有效分子与分母同步调整 |
| 确认无有效人物 | 完成率 100%，标签为无需后续处理，不增加实际发布人数 |
| 批量操作中有一条不满足条件 | 整批不提交，明确指出问题 |
| 人物改名、同名人物、同日多项目 | 关联稳定，不错误合并 |
| 关闭重开浏览器、释放资源、挂起与恢复 | 数据和可推导进度保持一致 |
| 卡片展开／收回、自动换列、筛选重排与批量更新 | 过渡风格参考 Trello Pro，变化可追踪，数据正确性不依赖动画完成 |
| 动画中连续操作、浏览器不支持过渡能力、开启减少动态效果 | 不残留遮罩或错位，操作可用，按规则简化或关闭位移动画 |

**JSON 必须用真实文件做往返验收：** 从浏览器实际导出文件，读取落盘文件检查内容，再在隔离测试环境中从该文件恢复，逐项比较业务字段、稳定 ID 和关联关系。不能只用内存对象序列化测试代替，也不能只凭出现“导出成功”提示判定通过。

另外使用真实的损坏文件、未知版本文件和断裂关联文件验证拒绝恢复，并检查失败后原数据仍然完整。

首版完成标准保持不变：用少量数字和人物操作准确管理摄影工作，双视图一致，状态解释明确，备份能够完整恢复。
